# 1번 위협 범위 — RED 중심 설계안

상태: **설계 제안, 사용자 최종 승인 전**  
코드 구현 상태: 이번 문서 작성 시점에는 새 코드를 추가하지 않음

## 사용자가 선택한 위협 범위

v1은 다음 공격자를 고려한다.

- 같은 Windows 사용자 권한으로 실행 중인 별도 프로세스
- 금고 파일 경로와 main/WAL/SHM을 알고 있음
- unlock 중 파일을 교체·증가·truncate하거나 같은 길이로 바꿀 수 있음
- 정상 앱 `.lock` 규약을 따르지 않음

이번 범위에서 공격자가 자동으로 가진 것으로 보지 않는 권한:

- 관리자/SYSTEM 권한
- KeyAtlas 프로세스 내부 임의 코드 실행
- 잠금 해제된 프로세스 메모리의 무제한 읽기
- 운영체제 커널 장악

완전한 same-user malware는 다른 경로로 메모리·화면·클립보드를 노릴 수 있다. 따라서 이 설계는 “로컬 악성코드 완전 방어”가 아니라 **SQLite raw-file 경쟁 경계의 방어 심화**다.

## 현재 관찰된 구조적 문제

1. 앱은 main/WAL/SHM을 별도 `std::fs::File`로 사전 검사한다.
2. 그 뒤 rusqlite가 같은 경로 문자열을 다시 연다.
3. 사전 검사 핸들과 SQLite 실제 main/WAL/SHM I/O가 하나의 capability로 결속되지 않는다.
4. 첫 application SQL 전후에 sidecar가 생성·증가·교체될 수 있다.
5. RO gate를 drop하고 경로로 RW connection을 다시 열기 때문에 승격 시 결속이 끊어진다.

경로, mtime, 길이, 사후 해시를 더 자주 확인하는 것만으로는 이 경쟁을 제거할 수 없다. 검사 사이에 바뀌었다가 돌아오는 ABA와 같은 길이 변조가 남는다.

## 접근안 비교

### 접근안 A — 위험한 existing DB를 모두 fail-closed

안전을 증명할 수 없는 sidecar나 active writer가 있으면 열지 않는다.

- 장점: 구현이 가장 빠르고 원본을 보존하기 쉽다.
- 단점: 정상 crash-WAL도 거부할 수 있고 기존 금고를 실사용하기 어렵다.
- 판정: 구현 전 임시 release gate로는 필요하지만 최종 제품 해법은 아니다.

### 접근안 B — custom VFS로 원본을 직접 검사·사용

Windows 기본 VFS를 감싸는 최소 wrapper가 actual main/WAL/SHM open과 I/O를 검증한다. RO 검사와 RW 쓰기를 모두 원본에서 수행한다.

- 장점: 복사 비용이 없고 기존 SQLite WAL semantics를 보존하기 쉽다.
- 단점: 공격자 입력을 검사하는 SQL과 원본 I/O가 같은 연결에 남아 있어 구현·감사 복잡도가 높다.
- 판정: 가능한 최종안이지만 preflight 경계가 덜 단순하다.

### 접근안 C — custom VFS + private in-memory snapshot

custom VFS로 source의 실제 파일 집합을 먼저 결속한 뒤, 정상 SQLite read transaction과 Backup API로 private in-memory snapshot을 만든다. 구조 검사·무결성 검사·비밀번호 인증은 snapshot에서만 수행한다. 인증 성공 뒤 원본 RW 승격은 다시 같은 VFS policy와 file-set epoch로 검증한다.

- 장점: 공격자-controlled source를 오래 query하지 않고, 잘못된 비밀번호에서 원본 무쓰기를 가장 명확하게 분리한다.
- 단점: unlock 시 메모리·복사 시간이 증가하고, source VFS와 RW 승격 경계도 여전히 정확히 구현해야 한다.
- 판정: **현재 권고안**이다.

## 권고 아키텍처

```text
Trusted LocalAppData capability
          ↓
Application StoreLock
          ↓
Windows Bound SQLite VFS
  - actual handle identity
  - no reparse / fixed local volume
  - role + size + share policy
  - main/WAL/SHM I/O mediation
          ↓
Bound source read transaction
          ↓
Private in-memory SQLite snapshot
          ↓
schema / integrity / caps / auth
          ↓ 인증 성공만
RW promotion with same VFS policy
          ↓
BEGIN IMMEDIATE + epoch/digest recheck
          ↓
Writable store retaining guard
```

## 상세 데이터 흐름

### 1. 위치와 앱 잠금

기존 `TrustedLocalAppDataRootV1`과 `StoreLockV1`을 유지한다. UNC, mapped drive, cloud/sync 위치, reparse, unknown drive type은 fail-closed한다.

### 2. VFS 등록과 actual file-set 결속

작고 독립된 Windows native crate가 SQLite 전용 VFS를 등록한다. `unsafe`와 FFI는 이 crate 안에만 둔다. store crate는 계속 `forbid(unsafe_code)`를 유지한다.

VFS는 main과 WAL open 시 actual HANDLE을 직접 소유하고, file ID, volume, final path, 파일 역할, 허용 크기를 capability에 기록한다. SHM은 pathname 재확인만으로 끝내지 않고 `xShmMap/xShmLock` 경계에서 정책을 적용한다.

기본 Windows VFS에 path open을 맡긴 뒤 metadata만 다시 확인하는 shim은 완료 조건이 아니다. 기존 raw writer나 writable mapping이 있으면 write/delete sharing을 확보하지 못해 첫 SQL 전에 실패해야 한다. 처음 없던 WAL/SHM namespace를 공격자가 먼저 차지하는 race도 수락하지 않는다. 구체적인 reservation 방식은 정상 SQLite WAL semantics와 함께 native prototype으로 증명해야 한다.

검증을 지원할 수 없는 SQLite/Windows 상태에서는 약한 fallback을 사용하지 않는다. VFS가 획득된 뒤 외부 write/delete/writable mapping이 성공하거나, SQLite I/O 하나라도 VFS가 소유하지 않은 path-reopened handle을 사용하면 설계 실패로 판정한다.

### 3. source read snapshot

첫 application-level 검사 SQL 전에 source actual main handle family 결속을 끝낸다. WAL recovery/open도 전용 VFS 경계를 지나야 한다. bare `BEGIN`은 deferred이므로 transaction 문자열 실행만 snapshot 고정 증거로 사용하지 않는다. 외부 raw writer를 OS sharing 경계에서 차단한 뒤 실제 첫 read를 수행하고 private in-memory destination으로 Backup API를 수행한다.

부분 backup, cancel, I/O error, panic은 검증 완료 snapshot 타입으로 승격할 수 없다.

### 4. 구조 검사와 인증

application ID, user version, schema fingerprint, bounded integrity, row/byte caps, foreign-key, password envelope, current revision 인증을 private snapshot에서 수행한다.

잘못된 비밀번호에서는 source RW connection을 만들지 않고 snapshot과 source RO connection을 닫는다. 원본 main/WAL/SHM의 허용되지 않은 변화가 없어야 한다.

### 5. RW 승격

인증 성공 뒤에도 즉시 신뢰하지 않는다. RO source가 기록한 file-set epoch와 logical digest를 보유한 채, 같은 VFS policy로 writable connection을 연다.

`BEGIN IMMEDIATE` 안에서 actual file-set identity, schema, row caps, envelope graph, logical digest를 다시 확인한다. 하나라도 달라졌다면 쓰지 않고 conflict/preservation 오류로 끝낸다.

### 6. store lifetime

성공한 store는 raw `rusqlite::Connection`만 가지면 안 된다. connection과 함께 VFS/file-set guard, app lock, epoch를 private 필드로 보유한다. 외부 API는 raw handle이나 raw connection을 꺼낼 수 없어야 한다.

## 오류 처리

| 상태 | 동작 |
| --- | --- |
| actual handle mismatch | 첫 application SQL 전에 종료, 원본 보존 |
| WAL/SHM policy 불명확 | `UnsupportedFileState` 계열로 fail-closed |
| size/read budget 초과 | bounded 오류, 원본 보존 |
| wrong password | 잠긴 상태 유지, RW open 금지 |
| future version | upgrade-required 보존 상태 |
| current corruption | corrupt 보존 상태, 자동 수정 금지 |
| RO→RW epoch/digest 변화 | concurrent-change 오류, 쓰기 금지 |
| backup 중단 | 부분 snapshot 폐기, 원본 보존 |
| VFS/FFI 기능 미지원 | 약한 fallback 없이 unsupported |

오류와 로그에는 경로 전체, 사용자 이름, Secret, ciphertext, SQL value를 넣지 않는다.

## 이 설계로 해결되지 않는 것

- 완전한 same-user process-memory compromise
- 커널/관리자 권한 공격자
- 과거에 정상 서명된 DB/WAL 전체 rollback
- 전체 record/revision omission
- 악성 업데이트와 공급망 공격
- 복구 수단 탈취와 계정 takeover
- process injection, handle duplication, 관리자·커널·raw-volume write
- 가용성 DoS

따라서 VFS 작업이 끝나도 실제 Secret gate를 곧바로 열지 않는다. rollback/omission anchor와 recovery/device 보안이 다음 P0다.

## 승인 기준

권고안은 **접근안 C**다. 다만 Daybreak 검토에 따라 “metadata-checking wrapper”가 아니라 **actual handle family를 소유하는 VFS**로 정의한다. 사용자 승인 후 저장소에 정식 design spec을 작성하고, 구현 plan으로 전환한다.
