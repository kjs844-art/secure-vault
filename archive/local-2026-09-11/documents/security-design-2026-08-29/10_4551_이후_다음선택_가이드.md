# KeyAtlas 4551 이후 다음 선택 가이드

업데이트: 2026-08-31 01:27 KST  
현재 결론: **Smart App Control은 유지하고, Phase 0A는 Inconclusive로 둔다.**

## 30초 요약

`cargo test`의 Rust 테스트 EXE가 코드 assertion에서 실패한 것이 아니다.
Windows Smart App Control이 디지털 서명이 없는 새 EXE를 실행 전에 막았다.

따라서 다음 작업은 보안 기능을 끄는 것이 아니라 아래 세 경로 중 하나를
사용자가 승인한 뒤 별도 계획으로 진행하는 것이다.

1. 신뢰된 RSA 코드 서명 파이프라인
2. 전용 Windows 검증 환경 계약
3. broker/service-boundary 재설계

## 현재 확정된 것과 아직 모르는 것

### 확정됨

- Code Integrity 이벤트 `3033/3077/3089`가 정확한 test EXE를 가리킨다.
- 정책은 Smart App Control `VerifiedAndReputableDesktop`다.
- 이벤트 SHA-256 Flat Hash와 실제 EXE SHA-256이 일치한다.
- EXE는 `NotSigned`이고 correlated signature count는 `0`이다.
- 이 환경 원인이 ordinary suite를 실행 전에 막았다.

### 아직 증명되지 않음

- 실행만 허용하면 ordinary suite가 통과하는지
- full SQLite VFS가 안전한지
- 실제 main/WAL/SHM 경쟁과 복구가 안전한지
- 실제 비밀번호/API 키 입력을 열어도 되는지

## 선택 A — 신뢰된 RSA 코드 서명

### 쉬운 비유

Windows 경비원에게 테스트 EXE마다 공인된 출입증을 붙이는 방식이다.

### 필요한 것

- Microsoft Trusted Root Program에 연결되는 상용 code-signing 인증서 또는
  적격 Artifact Signing Public Trust 계정
- Cargo가 만드는 library test, integration test, helper EXE를 최종 링크 뒤
  빠짐없이 서명하는 자동화
- 실행 전 signature 검증과 실패 시 fail-closed 처리
- 인증서 비용·계정·조직/개인 자격·키 보관 결정

2026-08-31 Microsoft 공식 조건상 Artifact Signing Public Trust는 한국의
**조직**에는 제공되지만, **개인 개발자**는 미국·캐나다 거주자만 대상이다.
따라서 한국 개인 계정이라면 상용 CA 인증서 또는 적격 조직 계정이 필요할 수
있다. 가입 시점에 [공식 Quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart)를
다시 확인해야 한다.

### 장점

- 현재 물리 PC의 Smart App Control enforcement를 유지할 수 있다.
- 현재 pinned host에서 ordinary suite를 실행할 가능성이 가장 높다.

### 단점

- 인증서와 계정 비용·자격 조건이 있다.
- Cargo test 산출물마다 서명이 필요해 파이프라인이 복잡하다.
- Authenticode 서명은 최종 PE 바이트를 바꾸므로, 서명된 생성 PE를 허용하도록
  gate 계약을 명시적으로 개정·재승인해야 한다.

### 판정

가장 직접적이지만, 돈·계정·공급망 보안 검토가 필요하다. 자동 구매나 등록은
하지 않는다.

## 선택 B — 전용 Windows 검증 환경

### 쉬운 비유

일상용 PC의 강한 경비는 그대로 두고, 개발 실험 전용 방을 별도로 만드는 방식이다.

### 두 종류

1. GitHub Actions `windows-latest`
   - ordinary tests가 다른 Windows 환경에서 실행되는지 확인하는 **보조 증거**
   - 현재 pinned host 판정을 자동으로 통과시키지 않음
2. 전용 Windows VM/개발 기기
   - OS·Rust·SQLite·보안 정책을 정확히 고정하는 새 검증 환경
   - 권위 환경으로 쓰려면 기존 계획을 수정하고 다시 승인해야 함

### 장점

- 현재 물리 PC의 Smart App Control을 약화하지 않는다.
- 반복 테스트와 CI 기록을 만들기 쉽다.

### 단점

- 현재 계획의 Windows `10.0.26200.0` pinned-host와 다른 환경이다.
- VM/CI가 통과해도 기존 Phase 0A를 몰래 Pass로 바꾸면 안 된다.

### 판정

개발 속도와 안전의 균형이 가장 좋다. 단, “보조 CI”와 “권위 검증 VM”을
구분해야 한다.

## 선택 C — broker/service-boundary 재설계

### 쉬운 비유

SQLite 파일을 여러 프로세스가 직접 만지지 못하게 하고, 한 명의 금고 담당자만
파일을 열도록 구조 자체를 바꾸는 방식이다.

### 장점

- actual-handle VFS의 복잡한 main/WAL/SHM 경쟁을 제품 경계 밖으로 밀어낼 수 있다.
- 단일 프로세스·단일 소유권을 강하게 만들기 쉽다.
- 현재 승인된 프로젝트 Phase 0A 계획이 Inconclusive일 때 정한 후속 경로다.

### 단점

- IPC, service lifetime, crash recovery, 인증, 업데이트 설계를 새로 해야 한다.
- 구현량이 늘고 모바일·웹 구조와 연결할 때 추가 설계가 필요하다.

### 판정

가장 큰 구조 변경이지만 장기적으로는 보안 설명이 단순해질 수 있다.

## 추천 순서

```text
1. Smart App Control 유지
   ↓
2. 보조 Windows CI 계획을 먼저 검토
   ↓
3. 사용자가 아래 하나를 선택
   ├─ 인증서/계정 비용 허용 → A 서명 파이프라인 설계
   ├─ 새 권위 VM 허용       → B 검증 환경 계약 개정
   └─ 둘 다 원치 않음       → C broker 재설계
```

보조 CI를 추가하더라도 explicit hard gate는 실행하지 않는다. ordinary suite만
실행하며, 다른 호스트의 성공을 현재 pinned-host Pass로 기록하지 않는다.

## 사용자가 나중에 결정해야 할 것

- 코드 서명 인증서나 Artifact Signing에 비용을 쓸지
- 개인 계정 또는 조직 계정 중 무엇을 사용할지
- 별도 Windows VM/개발 기기를 권위 검증 환경으로 인정할지
- 현재 actual-handle VFS 방향을 계속할지 broker 구조로 돌아갈지

## 에이전트가 승인 전 혼자 할 수 있는 것

- 각 경로의 위협 모델과 상세 구현 계획 초안 작성
- CI YAML 초안 작성과 action SHA 조사 — **활성화는 별도 승인**
- signing pipeline의 입력·출력·실패 경계 설계
- broker IPC 프로토콜과 crash/recovery 테스트 설계
- RED/BLUE 독립 문서 검토

## 사용자 승인 전 하지 않는 것

- Smart App Control Off/Evaluation 전환
- registry 또는 `.cip` 변경
- Secure Boot/Defender/TESTSIGNING 약화
- 인증서 구매·클라우드 계정 생성·파일 외부 제출
- workflow 생성·push·GitHub Actions 실행

## 검증 게이트 통과 전 하지 않는 것

- one-time hard gate 재실행
- 실제 Secret 입력과 store integration
- Draft PR의 Ready 전환 또는 `main` 병합

사용자 승인만으로 병합할 수 있는 것이 아니다. 현재 pinned-host ordinary suite가
exit `0`으로 통과하거나, 별도로 승인된 새 권위 검증 계약이 그 계약의 gate까지
통과해야 한다.

Consumer Smart App Control에는 개별 앱 bypass가 없다. self-signed/로컬 루트,
Public Trust Test/Private Trust, 임의 supplemental `.cip`, 경로/파일명 변경을
이 gate의 우회로 인정하지 않는다.
