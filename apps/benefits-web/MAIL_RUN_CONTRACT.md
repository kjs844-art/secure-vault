# Gmail 실행 제어 — 동의·소유권·한도·취소

2026-09-28. `runMailAnalysis`는 서버 내부의 provider 독립 실행 제어 코드다.
실제 로그인/OAuth/메일/AI/DB 구현은 아니며 공개 라우트에 연결되지 않았다.
인증 fixture와 quota ledger는 테스트에만 있다. `REAL_SECRET_GATE=CLOSED`.

## 전체 흐름에서의 위치

```text
향후 서버 라우트: 실제 검증된 로그인 요청 + 서버 설정
  ↓ (아직 연결하지 않음)
runMailAnalysis
  → 인증 principal/연결된 Gmail/두 동의 확인
  → 일회 실행 권한 + 사용량 한도 원자적 차감 어댑터
  → 권한 재확인 → 제한된 메일 조회 어댑터
  → 권한 재확인 → 순수 메일 정규화
  → 권한 재확인 → 외부 분석 어댑터
  → 권한 재확인 → 순수 후보 검증 → 최종 권한 재확인
  → 검토 전 후보 + 이번 호출의 처리 관찰 기록
```

실제 공급자를 호출하는 어댑터 대신 합성 구현을 주입해 위 순서를 시험한다.
사용자 확인·서비스/혜택 저장·계정 생성은 이 함수에 포함하지 않았다.
`extractedAt`은 분석 완료 관찰 시각이며 메일 수신일/내용의 관찰일을 대신하지 않는다.

## 어댑터가 반드시 보장할 것

| 어댑터 | 실제 구현에서 필요한 계약 |
|---|---|
| `readAuthority` | 해당 요청의 실제 검증된 principal + 신뢰 저장소. 호출자 JSON의 userId/role/consent는 인증 근거가 아님 |
| `reserveQuota` | 사용자/세션/메일 연결/분석 수신자/정책/동의 revision/만료/숫자 한도를 한 트랜잭션에서 검사하고 일회 실행을 차감 |
| `readMailbox` | 같은 소유자의 승인된 OAuth connection만 조회, 전송 직전 권한 재확인, 고정 query/최대 30개/FULL로 제한, 응답 stream 크기 제한 |
| `analyze` | 전송 직전 private context로 재확인, 승인 recipient만 사용, 정규화된 메일만 payload로 구성, 응답 stream 크기 제한, 도구 실행 없는 모델 호출 |

함수는 고정 snapshot의 필드/동의/만료/결합을 검사하지만, 어댑터가 검증되지 않은
사용자 입력을 진짜 인증 정보처럼 반환하는 것까지 해결하는 인증 시스템이 아니다.
어댑터·authority 객체를 HTTP 요청 body에서 주입하는 라우트를 만들면 안 된다.

메일 조회 범위 v1은 최근 2년의 welcome/trial/coupon/credit/receipt/subscription
영문 제목 검색과 최대 30개다. 전 세계 모든 가입 사이트를 확인하는 기능이 아니다.
OAuth의 제공자 권한 범위와 이 앱의 query 제한은 다르다. query만으로 Google 자체가
특정 라벨/메일에만 접근 권한을 부여했다고 표현하면 안 된다.

## 동의와 결합

- `ownerId`와 `sessionId`는 검증된 로그인에서만 나온다.
- `grantOwnerId`, `grantSessionId`, `grantMailboxBindingId`가 선택한 사용자/세션/메일 연결과
  같아야 한다. 연결 ID는 불투명한 서버 참조이지 메일 주소·OAuth 토큰이 아니다.
- `mailRead`와 `externalAnalysis`를 독립적으로 선택·확인해야 한다. Google 연결 성공이나
  메일 읽기 동의를 외부 AI 전송 동의로 자동 확장하지 않는다.
- 현재 resolver 계약은 두 동의를 검사한 aggregate grant snapshot을 반환한다.
  하나라도 변경/철회되면 revision이 바뀌어야 하며 만료는 둘 중 이른 시각이어야 한다.
  boolean 두 개만 전달했다고 실제 동의 UI/저장이 구현된 것은 아니다.
- 동의는 `operationId`, 메일 연결, 분석 수신자 `recipientId`, 고정 정책 버전에 묶인다.
  기본 실행은 한 번이다. 수신자/범위가 바뀌면 이전 승인을 재사용하지 않는다.
- auth/consent snapshot과 옵션은 명시한 필드만 복사하여 동결한다. 추가 adapter 필드와
  자격증명을 다른 단계/결과에 무조건 펼쳐서 전달하지 않는다.
- 분석 어댑터에는 전송 권한을 재확인할 **private RunContext**를 준다. 이것을 모델에
  직렬화하지 않는다. 실제 제공자 payload projection 검증은 후속 어댑터 작업이다.

## 한도와 중복 실행

quota 응답은 정확한 `granted` 구조 또는 `{status: "denied"}`만 허용한다.
모르는 값, null, 음수/비정수 잔여량, 다른 소유자/세션/메일/동의/실행 식별자는 거부한다.
남은 횟수 0은 마지막 허용 실행을 이미 차감한 정상 값일 수 있다.

일회 사용 key는 최소 `(ownerId, operationId)`다. 세션/동의 revision이 바뀌어도 같은
operation을 다시 차감해 실행하면 안 된다. 병렬 중복 실행은 DB 트랜잭션·unique 제약 등
실제 저장소가 원자적으로 막아야 한다. 테스트의 메모리 ledger는 그 계약을 시험하는 예이며
여러 서버 인스턴스에서의 실제 동시성 보장이 아니다.

quota 단계 이후 실패하더라도 자동 환불/재시도를 하지 않는다. 차감 결과가 불명확하면
`unknown`을 남긴다. 외부 처리 비용과 사용량 복구는 영속 ledger로 나중에 대조해야 한다.

## 취소·만료·시간 제한

- 기본 전체 실행 제한 30초, 서버 옵션 최대 120초. 개별 단계마다 다시 30초로 늘리지 않는다.
- 전체 실행 제한과 알려진 권한 만료 모두 타이머와 monotonic deadline 비교를 함께 사용한다.
  동기 처리/microtask 때문에 타이머가 지연되어도 다음 어댑터 호출 직전과 최종 반환 전에
  직접 비교한다. 이미 만료된 권한으로 다음 호출을 시작하거나 성공 결과를 반환하지 않는다.
- 알려진 세션/동의 만료가 더 빠르면 그 시각에 abort를 요청한다.
- 사용자 취소·timeout 후 늦은 resolve/reject는 다음 단계나 후보 반환을 재개하지 않는다.
- 동의 철회/사용자·세션·정책 변경은 매 비동기 경계와 최종 반환 전에 다시 확인한다.
  원격 철회 push 이벤트를 받는 시스템은 아직 없으므로 **대기 중 실시간 철회 탐지**는 아니다.
- 마지막 검증과 실제 원격 send 사이의 경쟁 조건을 이 함수만으로 없앨 수는 없다.
  어댑터의 dispatch 재검증·권한 취소/이벤트 결합이 필요하다.
- abort를 무시하는 공급자의 작업·요금·메모리 보유를 강제로 중단하거나, 이미 전송한
  데이터를 회수한다고 보장하지 않는다. JavaScript zeroization도 보장하지 않는다.

## 처리 기록의 정확한 의미

`receipt`는 비영속 호출 관찰이다. 원문/토큰/예외 stack은 없으며, 처음 확인한 실행·메일
참조·분석 수신자·동의 ID/revision/시각을 포함한다. 이 참조들도 사용자 메타데이터이므로
나중에 실제 API로 반환/저장할 때 소유권 제한이 필요하다.

| 값 | 의미 |
|---|---|
| `authorityAtStart: null` | 시작 권한 snapshot을 확인하지 못함 |
| `quota: not-consumed` | **이번 호출에서** 새로 차감하지 않았음. 이전에 사용한 operation의 replay 거부일 수도 있음 |
| `quota: unknown` | 차감 요청은 시작했지만 결과를 신뢰할 수 없음 |
| `quota: consumed` | 결합이 맞는 허용 응답을 받음. 실제 DB 증거는 어댑터 구현 후 별도 검증 |
| `not-started` | 해당 adapter를 호출하지 않음 |
| `started` | 호출 시작. provider 완료/미완료 여부를 확정하지 못함 |
| `returned` | adapter 응답 도착. 올바른 내용·전송 완료·실제 계정 상태를 증명하지 않음 |
| `undoAvailable: false` | 전송 회수/차감 복구가 구현된 것처럼 보이는 취소 버튼을 제공하지 않음 |

로그인/동의/실행 기록의 영속 보관, crash 복구, provider 완료 증명, 삭제와 보존 기간은
후속 구현이다. receipt만으로 그 기능이 완료됐다고 하지 않는다.

이 설계에는 `agent-consent-patterns`의 좁은 권한, 독립 동의, 수신자·범위의 구체화,
일회 권한, 외부 한도 강제, 정직한 철회/처리 기록 원칙을 반영했다. 최종 UI/디자인은 하지 않았다.
