# Security Architecture

## 정직한 보안 약속

서버는 사이트명, URL, 아이디, 비밀번호, API 제공자, Secret 원문, 태그, 메모처럼 의미 있는 금고 내용을 평문으로 알 수 없어야 합니다. 다만 계정 인증 정보, IP, User-Agent, 요청 시각, 암호문 크기, 저장량, 활성 암호화 레코드 슬롯 수, 같은 불투명 슬롯의 revision 빈도와 삭제 시각 같은 운영 메타데이터는 볼 수 있습니다.

## 계정과 금고의 분리

- Google OIDC와 passkey는 서비스 계정 인증에 사용합니다.
- 별도의 금고 마스터 비밀번호가 금고 잠금 해제에 사용됩니다.
- 로그인 토큰이나 Google 비밀번호로 금고 루트 키를 직접 만들지 않습니다.

## 키 계층

- 클라이언트가 CSPRNG로 무작위 Vault Root Key를 생성합니다.
- 마스터 비밀번호는 기기에서 보정한 Argon2id로 KEK를 만들고 루트 키를 감쌉니다.
- 오프라인 복구 키는 별도 KEK와 Key Slot을 만듭니다.
- 기본 보호 수단은 마스터 비밀번호와 오프라인 복구 키입니다. 실제 Secret 저장 전 hardware-backed로 검증된 신뢰 기기, 지원되는 물리 보안키, 복구 보호자 중 최소 한 종류를 추가하고 복구 연습을 완료해야 합니다. software-backed 기기에는 독립 Root Key Slot을 발급하지 않으며 마스터 비밀번호나 다른 고보증 경로로 매번 잠금 해제합니다.
- 각 신뢰 기기는 비반출 기기 키와 폐기 가능한 별도 Key Slot을 사용합니다. 물리 보안키는 WebAuthn PRF 또는 CTAP2 `hmac-secret`처럼 Root Key 복호화에 실제 참여하는 기능이 검증된 경우만 복구 수단으로 인정합니다.
- 기기 roster는 `sync_client`와 `recovery_authenticator` 역할을 분리하고 한 기기가 둘 다 가질 수 있게 합니다. 상품의 동기화 기기 한도는 `sync_client`에만 적용하며 복구 인증기 Slot을 결제 상태로 비활성화하지 않습니다.
- 복구 보호자는 세 명 중 두 명 정족수, 7일 대기, 전체 알림과 취소를 적용하며 구체 암호 구성의 별도 ADR·독립 검토 전에는 활성화하지 않습니다.
- 각 항목은 무작위 Item DEK를 사용하고, 항목 내용과 의미 있는 메타데이터 전체를 AEAD로 암호화합니다.
- 레코드 암호화는 XChaCha20-Poly1305를 기본 후보로 하며, 알고리즘·라이브러리·파라미터는 독립 검토와 테스트 벡터 승인 후 안정화합니다.
- 프로토콜 버전, vault 식별 commitment, item/revision/epoch 식별자를 AAD에 포함해 바꿔치기를 막습니다.

## 클라이언트

- Rust 코어가 키 파생, 봉투 암호화, 이벤트 검증, 직렬화 계약을 담당합니다.
- Android는 Kotlin과 Android Keystore의 비추출형 기기 키를 사용하며, 생체 인증은 키 사용 승인을 담당합니다.
- 웹은 Rust/WASM을 사용합니다. 암호문만 IndexedDB에 저장하고 잠금 해제 중 검색 인덱스는 메모리에서 생성합니다.
- 웹 금고는 별도 origin, 엄격한 CSP·Trusted Types, 제3자 스크립트 금지, 짧은 자동 잠금을 적용합니다. 동적 JavaScript 공급망 위험을 완전히 제거할 수 없음을 사용자에게 알립니다.

## 동기화

서버는 패딩된 불투명 이벤트와 암호화·서명 체크포인트를 보관하는 append-only 저장소로 동작합니다. 각 논리 항목은 클라이언트가 만든 무작위 `opaque_record_id`를 사용합니다. 서버는 그 의미를 모르지만 한도 계산과 revision 연결을 위해 동일 슬롯의 이벤트임은 알 수 있습니다. 상태 계산과 충돌 해결은 잠금 해제된 클라이언트가 수행합니다.

- 모든 변경은 서명 revision으로 append합니다. 보관기간이 지난 암호문 body는 검증된 checkpoint 뒤에 GC할 수 있지만 revision hash와 tombstone commitment는 남깁니다.
- 한도는 활성 슬롯 수와 서버가 직접 받은 billable 현재·이력 byte로 계산하고, bounded history safety reserve와 conflict reserve는 별도로 측정합니다. 암호문 속 실제 Secret 개수는 알 수 없고 보안 경계로 주장하지 않습니다.
- 다운그레이드 초과 상태의 보안상 필수 교체는 같은 슬롯·`expected_head_hash`·같은 패딩 버킷의 compare-and-append `safety swap`으로 처리합니다. 이전 body는 즉시 GC하지 않고 슬롯당 한 개의 history safety reserve에 수락 당시 보관기간만큼 유지합니다. reserve가 찬 추가 swap은 로컬 안전본으로 남기고 미동기화 상태를 표시합니다.
- 같은 head에서 갈라진 competing revision 한 개는 슬롯별 conflict reserve에 받아 최대 두 head까지만 서버에 보존합니다. 충돌 중인 body는 사용자 해결 전 GC하지 않습니다. 그 밖의 stale writer는 거부하되 암호화 값을 기기의 로컬 충돌 복구함에 보존하고 미동기화 상태를 표시합니다.

- 비밀번호, API 키, Secret, TOTP seed, 복구 코드는 절대 LWW나 문자열 병합하지 않습니다.
- 동시 변경은 두 값을 모두 보존하고 사용자가 명시적으로 해결합니다.
- 삭제와 오프라인 수정이 충돌하면 기본 목록에서는 삭제를 유지하고 수정본은 암호화 복구함에 남깁니다.
- 오래된 기기가 삭제 항목을 자동 부활시키지 못하도록 tombstone head를 체크포인트에 유지합니다.

## 기기 분실

분실 기기의 세션과 device roster 권한을 취소하고 새 무작위 Vault Root Key로 key epoch를 시작합니다. 전환은 이전 roster의 유효한 승인 또는 이전 Root Key 소유 증명과 인증된 전체 manifest를 요구하며, 모든 현재 ciphertext의 1:1 재암호화·업로드와 새 checkpoint 검증이 끝나기 전에는 구 epoch를 폐기하지 않습니다. 활성 보호 수단의 Key Slot을 새 Root Key로 다시 만들고, 현재 항목을 새 Item DEK로 다시 암호화합니다. 이미 분실 기기가 보았던 평문은 회수할 수 없으므로 외부 서비스 자격 증명 회전 체크리스트를 제공합니다.

마지막 선택 수단도 도난 시 즉시 폐기할 수 있습니다. 계정은 `보호 설정 필요` 상태로 전환하고 기존 항목 읽기·내보내기·삭제·회전은 허용하되, 대체 수단 등록과 복구 연습 전까지 새 Secret 추가를 중단합니다. 복구 수단 등록·교체·폐기는 요금제와 무관하게 제공합니다.

## 복구 한계

마스터 비밀번호와 사용자가 활성화한 복구 키·신뢰 기기·지원 물리 보안키·복구 보호자 경로를 모두 잃으면 운영자도 금고를 복구할 수 없습니다. 계정 로그인용 passkey는 Root Key 복호화에 실제 참여하지 않으면 금고 복구 경로로 계산하지 않습니다. 이 한계를 온보딩과 복구 훈련에서 명확히 보여 줍니다.
