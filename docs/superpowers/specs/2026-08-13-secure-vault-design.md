# Secure Vault 설계 명세

## 1. 목표와 성공 기준

Secure Vault는 여러 개발·AI 서비스의 로그인 정보, 비밀번호, API 키, Secret, MCP 자격 증명을 수십·수백 개 규모에서도 계층적으로 정리하고 Android와 웹에서 빠르게 찾아 활용하는 개인용 보안 금고다.

첫 제품 성공 기준은 합성 데이터로 다음 흐름을 완주하는 것이다: 계정 인증 → 별도 금고 생성·잠금 해제 → 항목 생성·검색·보기·복사 → Android 오프라인 사용 → 다중 기기 동기화 → 충돌 보존 → 암호화 백업·사용자 복구 → 분실 기기 폐기.

## 2. 범위

MVP는 개인 금고와 개발자 자격 증명에 집중한다. 카드·신분증·일반 파일, 팀 공유, 자동 입력, TOTP 생성, AI의 Secret 접근, 서버 검색은 제외한다. 긴급 연락처 복구는 개인 MVP 이후 제한 베타에서 별도 설계한다.

개발과 검증은 로컬 Docker 환경을 기준으로 한다. 공개 클라우드·결제·도메인 선택은 공개 배포 전 별도 배포 명세로 분리하며, 현재 단계에서는 어떤 유료 자원도 요구하지 않는다.

## 3. 시스템 경계

- `apps/android`: Kotlin UI, 오프라인 암호문 캐시, Android Keystore, BiometricPrompt
- `apps/web`: React/TypeScript UI, Rust/WASM 암호화, 암호문 IndexedDB, 메모리 검색 인덱스
- `crates/vault-crypto`: 키 계층, AEAD 봉투, 서명·검증, 결정적 직렬화와 테스트 벡터
- `services/api`: Spring Boot 계정 인증, passkey/WebAuthn, device roster, 불투명 이벤트·체크포인트 API
- PostgreSQL: 인증·운영 데이터와 불투명 blob 저장; 금고 평문·검색 토큰 저장 금지
- `contracts`: 버전이 지정된 wire envelope, 이벤트, checkpoint, 오류 계약

공개 블로그·광고·분석 코드는 금고와 같은 origin 또는 runtime에서 실행하지 않는다.

## 4. 인증·암호화·복구

Google OIDC와 passkey는 계정 인증에만 사용하고, 금고 잠금 해제에는 별도 마스터 비밀번호를 사용한다. 클라이언트가 무작위 Vault Root Key를 만들고 비밀번호 KEK, 복구 KEK, 신뢰 기기 키로 각각 감싼다. 항목별 무작위 DEK가 내용과 의미 메타데이터 전체를 AEAD로 암호화한다.

실제 Secret을 저장하기 전에 복구 키와 두 번째 passkey 또는 신뢰 기기를 등록하고 복구 확인 절차를 완료해야 한다. 모든 복구 수단 분실 시 운영자 복구는 불가능하다.

암호 프로토콜은 외부 검토 전 안정화했다고 주장하지 않는다. Rust와 WASM/Android 바인딩 사이에 동일한 테스트 벡터, 변조 거부, 버전 마이그레이션, KDF 기기 보정 테스트가 필수다.

## 5. 데이터와 동기화

사용자 모델은 서비스 → 계정 → 조직/워크스페이스/프로젝트 → 환경 → Secret/MCP의 계층을 사용하며 서비스 템플릿과 사용자 정의 필드를 지원한다. 검색용 설명 필드도 암호화하고, 잠금 해제한 기기에서만 로컬 인덱스를 만든다. Secret 원문은 기본 검색 대상이 아니다.

서버 동기화는 패딩된 append-only opaque event log와 암호화·서명 checkpoint를 사용한다. password, API key, secret, recovery code 충돌은 multi-value로 보존하고 사용자가 해결한다. 삭제 충돌 수정본은 암호화 복구함에 남기며 자동 부활시키지 않는다.

## 6. 오류와 안전 동작

- 인증 성공과 금고 잠금 해제 성공을 서로 대체하지 않는다.
- 복호화·서명·체인 검증 실패는 손상 또는 공격 가능성으로 처리하고 자동 덮어쓰지 않는다.
- 부모 이벤트 누락, epoch 불일치, 오래된 기기 쓰기는 격리하고 전체 재동기화 또는 사용자 복구 흐름으로 보낸다.
- 복사한 Secret은 가능한 플랫폼에서 제한 시간 후 클립보드 정리를 시도하되 OS 보장을 과장하지 않는다.
- 로그, 분석, 오류 보고에는 평문 필드와 사용자가 입력한 검색어를 남기지 않는다.

## 7. 검증과 출시 게이트

단위 테스트는 암호 테스트 벡터, tamper rejection, 키 래핑, 직렬화 호환성을 검증한다. 통합 테스트는 오프라인 편집, 동시 Secret 변경, 삭제 충돌, 체크포인트 복구, 기기 폐기, key epoch 회전을 검증한다. E2E 테스트는 Android와 웹의 잠금·재인증·자동 잠금·내보내기 흐름을 검증한다.

DB dump와 로그만으로 평문을 추론할 수 없어야 하며, Secret 충돌 손실·삭제 항목 부활·폐기 기기의 새 epoch 접근이 한 번이라도 재현되면 출시를 차단한다. 실제 Secret 공개 베타는 독립 보안 검토와 침투 테스트 이후에만 허용한다.
