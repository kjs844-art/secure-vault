# Secure Vault 복구·보호 수단 설계

- 상태: 사용자 승인
- 기준일: 2026-08-14
- 적용 범위: 개인 금고의 잠금 해제, 복구 수단, 기기 분실 대응
- 현재 구현 상태: 합성 데이터 전용 `v0alpha1`; 이 문서의 복구 기능은 아직 구현되지 않음

## 1. 목표

사용자가 마스터 비밀번호나 기기를 잃어도 여러 독립 경로로 금고를 복구할 수 있게 하면서, 서버 운영자 단독으로는 금고 평문을 복호화할 수 없게 한다. 각 완전한 복구 경로는 현재 세대의 Root Key를 열 수 있으므로 가장 약한 완전 경로가 전체 위험에 영향을 준다. 따라서 경로 수만 늘리는 것을 `5중 보안`이라고 부르지 않고, 모든 경로가 정해진 최소 보증 수준을 충족하게 한다.

이 문서에서 `보호 수단`은 평상시 잠금 해제와 복구에 쓰이는 전체 수단을 뜻한다. 실제 비밀번호 분실 시 사용하는 `복구 경로`는 오프라인 복구 키, 신뢰 기기, 물리 보안키, 복구 보호자다. 마스터 비밀번호는 평상시 잠금 해제 수단이다.

## 2. 등록 정책

모든 사용자는 다음 기본 수단 두 가지를 설정한다.

1. 마스터 비밀번호
2. 오프라인 복구 키

다음 선택 수단 세 가지 중 최소 한 가지를 추가한다.

3. 신뢰 기기 한 대 이상
4. 물리 보안키 한 개 이상
5. 복구 보호자 세 명 중 두 명 승인

사용자는 총 세 가지부터 다섯 가지 보호 수단을 선택할 수 있다. 신뢰 기기나 물리 보안키를 여러 개 등록해도 보호 수단 종류 수는 하나로 계산하고, 실제 등록 개수는 별도로 표시한다. 기본 두 가지와 선택 수단 한 가지 이상의 설정 및 복구 연습은 실제 Secret 저장의 필요조건이며, 독립 보안 검토를 포함한 별도 출시 게이트를 대체하지 않는다.

복구 수단의 등록, 교체, 폐기와 복구 연습은 요금제와 무관한 핵심 안전 기능이다. 구독 만료나 다운그레이드가 기존 보호 수단을 비활성화해서는 안 된다.

## 3. 검토한 대안

### 다섯 수단을 모두 요구

한 수단만 분실해도 사용자가 잠길 수 있어 거부한다.

### 모든 수단을 같은 단일 확인으로 취급

복구 경로 하나가 Root Key를 복구하는 `1-of-N 경로` 자체는 가용성을 위해 필요하다. 그러나 서버 로그인 한 번처럼 모든 경로를 같은 낮은 보증 수준으로 취급하는 방식은 거부한다. 각 완전 경로는 고엔트로피 비밀 또는 비반출 키를 가져야 하고, 경로에 따라 기기 사용자 확인, 계정 재인증, 보호자 정족수, 대기·알림을 추가한다.

### 기본 두 가지와 선택 세 가지

복구 가능성과 사용 편의의 균형이 가장 좋으므로 채택한다. 가입 흐름은 기본 수단을 먼저 만들고 사용자가 선택 수단을 한 가지부터 세 가지까지 추가하도록 안내한다.

## 4. 키 구조

클라이언트가 CSPRNG로 무작위 256비트 `Vault Root Key`를 생성한다. Root Key는 영구 고정 키가 아니라 `key_epoch`별 세대 키다. 실제 자격 증명 레코드는 항목별 무작위 `Item DEK`로 암호화하고, Item DEK는 현재 세대의 Root Key로 보호한다.

Root Key 원문을 서버에 저장하지 않는다. 각 보호 수단은 Root Key를 여는 별도의 암호화된 `Key Slot`을 만든다.

| 보호 수단 | Key Slot 원리 | 필수 안전 조건 |
| --- | --- | --- |
| 마스터 비밀번호 | Argon2id로 비밀번호 KEK를 만들고 Root Key를 AEAD로 감쌈 | 비밀번호 원문을 서버에 전송하거나 저장하지 않음 |
| 오프라인 복구 키 | CSPRNG로 만든 고엔트로피 복구 비밀에서 KEK를 파생 | 체크섬이 있는 인쇄·필기·오프라인 QR, 저장 확인 절차 |
| 신뢰 기기 | 검증된 하드웨어 보안영역의 비반출 개인키로 기기별 Slot 생성 | 생체정보는 키 생성 재료가 아니라 키 사용 승인에만 사용 |
| 물리 보안키 | WebAuthn PRF 또는 CTAP2 `hmac-secret` 결과로 KEK 파생 | 일반 FIDO 서명만 지원하는 키를 복호화 수단이라고 부르지 않음 |
| 복구 보호자 | Guardian Recovery Secret을 정족수 조각으로 분할 | 세 명 중 두 명, E2E 전달, 대기·알림·취소 |

각 Slot의 AEAD 추가 인증 데이터는 최소한 프로토콜 버전, vault commitment, slot ID, 수단 종류, key epoch와 suite version을 묶는다. 다른 사용자·금고·세대의 Slot로 바꿔 끼울 수 없어야 한다. 이 문서는 제품 정책을 고정하며 wire 계약을 고정했다고 주장하지 않는다. 구현 전 별도 wire ADR이 정확한 AEAD suite, canonical encoding, nonce·salt 길이와 유일성, KDF 파라미터·도메인, commitment 생성, 버전 하향 거부와 최대 크기를 결정하고 상호운용 테스트 벡터를 포함해야 한다.

신뢰 기기는 기기마다 별도 Slot과 폐기 가능한 기기 ID를 가진다. Android에서는 Android Keystore의 비반출 키를 사용하고, iOS에서는 Secure Enclave·Keychain 적합성을 별도 네이티브 설계에서 검증한다. 일반 브라우저 세션은 하드웨어 보호를 검증하기 전까지 고보증 신뢰 기기로 표시하지 않는다.

물리 보안키와 보호자 정족수의 구체 암호 구성은 각각 별도 ADR과 독립 검토를 통과한 뒤 구현한다. 장치 종속 보안키와 클라우드 동기화 passkey를 UI에서 구분하고, 후자는 검증 없이 `물리 보안키`나 특정 기기 전용 경로로 계산하지 않는다. 그전에는 UI에서 해당 수단을 사용 가능하다고 표시하지 않는다. 첫 구현은 사용자가 없는 합성 프로토콜 테스트이고, 그 다음 Android 한정 로컬 알파가 마스터 비밀번호, 오프라인 복구 키와 Android 신뢰 기기만 지원한다. Android를 포함한 모든 알파는 외부 독립 검토 전까지 합성 데이터 전용이며, 웹·iOS·데스크톱은 각 플랫폼의 선택 수단까지 구현한 뒤에도 같은 출시 게이트를 별도로 통과해야 한다.

## 5. 가입과 보호 설정

가입 흐름은 화면당 주 행동 하나를 사용하는 네 단계다.

1. 마스터 비밀번호 생성
2. 복구 키 저장 및 `복구 연습`
3. 선택 수단 한 가지 이상 등록
4. 현재 보호 상태와 영구 손실 조건 확인

화면은 `2/4` 같은 진행률, 약 3~5분의 예상 시간, 중단 후 재개를 제공한다. 복구 키는 앱 안에만 저장하지 말아야 한다는 점을 분명히 알린다. 원문을 다시 숨긴 뒤 사용자가 저장한 사본으로 일부 그룹을 확인해야 설정이 완료된다. 복구 키 화면은 분석·오류 보고를 완전히 비활성화하고, 플랫폼이 지원하면 화면 캡처를 억제한다. 갤러리·클라우드 클립보드·클라우드 프린터로 자동 전송하지 않으며, 사용자가 외부 카메라나 프린터로 만든 사본까지 통제할 수 있다고 주장하지 않는다.

완료 화면은 다음처럼 정확한 상태를 보여 준다.

- `보호 수단 3/5 · 신뢰 기기 2대`
- `마스터 비밀번호를 잊어도 복구 가능: 복구 키 또는 Galaxy S25`
- `영구 손실 조건: 표시된 모든 잠금 해제·복구 경로를 사용할 수 없음`

복구 수단 추가·교체는 최근 금고 잠금 해제와 강한 재인증을 요구한다. 변경 사실은 기존의 독립 알림 채널과 모든 활성 신뢰 기기에 전송하되 Secret, 사이트명, 계정명은 포함하지 않는다.

## 6. 잠금 해제와 복구 흐름

### 정상 잠금 해제

로컬 금고는 마스터 비밀번호 또는 이미 등록된 기기 키 사용 승인으로 잠금 해제한다. 동기화 계정 로그인과 금고 복호화는 별도 상태로 유지한다. Google OIDC나 서버 세션 성공만으로 Root Key를 얻을 수 없다.

### 오프라인 복구 키

동기화 계정에서는 계정 재인증 후 복구 키로 Root Key를 연 뒤 아래의 전역 `복구 사건`을 완료한다. 성공하면 새 마스터 비밀번호 Slot을 만들고 완료 사실을 모든 채널에 알린다.

로컬 암호화 export를 네트워크 없이 여는 작업은 `격리 복구본 열기`다. 고엔트로피 복구 키를 가진 사람이 이를 열 수 있으므로 복구 키 자체를 가장 강한 비밀 중 하나로 취급한다. 격리 복구본은 원래 서버 금고의 epoch·roster·Slot을 바꾸지 않고 처음에는 읽기·로컬 내보내기만 허용하며 동기화와 원래 금고에 대한 쓰기를 차단한다. 온라인으로 돌아오면 사용자는 계정 재인증 후 기존 동기화 금고의 전역 복구 사건을 완료하거나, 새 vault ID의 빈 금고를 만들고 명시적으로 항목을 재암호화해 가져온다. 오프라인에서 export를 연 사실만으로 전역 복구 완료나 알림 성공을 주장하지 않는다.

### 신뢰 기기

등록된 기기에서 OS PIN·생체 인증으로 비반출 기기 키 사용을 승인한다. 새 기기는 기존 기기와 근접 QR 또는 명시적 승인 채널로 연결하고, 사용자는 새 기기 이름과 키 지문을 확인한다.

Android 신뢰 기기 구현 전 별도 ADR은 다음 정책을 고정해야 한다.

- 매번 `BiometricPrompt.CryptoObject` 또는 동등한 강한 사용자 확인 뒤에만 키 사용
- hardware-backed 여부를 확인하고 software-backed 장치에는 독립 Root Key Slot을 발급하지 않음
- 앱 재설치, Keystore 키 삭제·무효화, OS 백업 복원과 화면 잠금 재설정 시 새 기기로 취급
- 생체정보 추가·변경 때 키를 유지할지 무효화할지 명시하고 해당 상태를 자동 테스트
- 개인키와 해제된 세션을 Android 백업에 포함하지 않음
- 루팅 탐지는 보조 신호일 뿐 안전 보장으로 사용하지 않음

실제 Secret 출시 조건에서는 hardware-backed 기기만 `신뢰 기기` 선택 수단을 충족한다. software-backed 기기는 동기화 클라이언트로 사용할 수 있지만 독립 Root Key Slot이나 단독 편의 잠금 해제를 제공하지 않고, 마스터 비밀번호 또는 다른 고보증 경로로 매번 금고를 연다. 별도 고보증 수단을 하나 더 등록했다는 이유만으로 software-backed Slot을 완전한 1-of-N 경로로 추가하지 않는다.

### 물리 보안키

지원되는 PRF 기능과 사용자 터치·PIN을 모두 확인한다. 보안키가 단순히 서버 로그인만 승인하고 Root Key 복호화에는 참여하지 않는 경우 이를 복구 수단으로 계산하지 않는다.

### 복구 보호자

세 명 중 두 명이 새 기기와 복구 요청을 승인해야 한다. 요청 후 기본 7일 대기, 모든 기존 기기·알림 주소 통지, 대기 중 사용자 취소를 적용한다. 보호자 한 명이나 운영자 단독으로는 복구 비밀을 재구성할 수 없어야 한다. 보호자 두 명의 공모 가능성은 구조적 한계로 공개한다.

### 복구 완료 상태 전이

신뢰 기기가 정상적으로 금고를 열 수 있는 상태에서 마스터 비밀번호만 바꾸는 것은 `잠금 해제 후 자격 증명 변경`이다. 새 비밀번호 Slot을 검증한 뒤 이전 비밀번호 Slot을 폐기하며, 수단 침해 징후가 없다면 전체 key epoch를 바꾸지 않는다.

복구 키·물리 보안키·보호자 경로를 사용하거나, Root Key를 단독으로 열 수 있던 device·recovery Slot을 이유와 무관하게 폐기하거나, 마스터 비밀번호 침해가 의심되는 작업은 `복구 사건`이다. 새 Slot 추가와 침해 징후 없는 마스터 비밀번호 Slot의 검증된 원자적 교체만 예외로 현재 epoch를 유지한다. 복구 사건은 다음 원자적 순서를 따른다.

1. 복구 클라이언트가 새 device signing key와 wrapping key를 생성
2. 새 무작위 Root Key와 증가한 `key_epoch` 생성
3. 이전 checkpoint의 인증된 전체 item-head·tombstone manifest와 모든 대상 ciphertext를 확보·검증
4. 현재 모든 항목을 새 Item DEK로 다시 암호화
5. 계속 신뢰할 보호 수단마다 새 epoch Key Slot 생성
6. 사용한 경로와 무관하게 새 오프라인 복구 키를 생성하고 새 사본 확인을 완료한 뒤 이전 복구 키 Slot을 폐기 대상으로 표시
7. 이전 epoch 소유 증명을 포함한 transition manifest와 새 roster·checkpoint를 검증·확정
8. 이전 인증 세션, refresh token, 진행 중 복구 요청, 이전 Slot과 구세대 쓰기 권한 폐기
9. 모든 기존 알림 채널에 완료 통지

활성 신뢰 기기는 새 epoch를 명시적으로 받아야 계속 사용할 수 있다. 오래 오프라인이던 기기는 자동으로 재가입하지 않고 전체 재동기화 또는 사용자 승인 흐름으로 보낸다. 과거 epoch 암호문과 이미 노출된 평문은 새 키 생성으로 회수되지 않는다.

transition manifest는 이전 checkpoint hash, 이전·새 key epoch, 전체 manifest hash, 새 roster, 새 Slot commitment와 새 checkpoint hash를 묶는다. 이전 roster의 유효한 승인 또는 이전 Root Key에서 도메인 분리한 transition-auth proof가 있어야 하며, 새 기기가 자기 키로 자기 roster만 서명하는 것은 승인으로 인정하지 않는다. 정확한 proof 구성과 서버 검증용 commitment는 후속 wire ADR과 테스트 벡터로 고정한다. 서버 로그인 세션만 탈취한 공격자는 기존 vault ID의 epoch를 바꿀 수 없어야 한다.

부분 캐시 기기는 이전 checkpoint manifest의 모든 head와 tombstone을 다운로드·검증하기 전 전환을 시작할 수 없다. 새 ciphertext 업로드와 새 manifest의 1:1 대응, 서버 저장 확인과 새 checkpoint 검증이 모두 끝날 때까지 구 epoch를 유지하는 snapshot barrier를 적용한다. 서버가 항목을 누락하거나 manifest가 맞지 않으면 전환을 중단하고 이전 epoch를 폐기하지 않는다.

## 7. 분실·교체·실패 처리

- 복구 키가 노출되면 새 키를 만들고 새 사본 확인을 통과한 뒤 이전 Slot을 폐기한다.
- 신뢰 기기를 분실하면 다른 수단으로 재인증해 즉시 device roster에서 폐기한다.
- 물리 보안키를 분실하면 해당 Slot만 폐기하고 대체 키를 등록한다.
- 보호자 구성이 바뀌면 기존 조각 전체를 폐기하고 새 정족수 세트를 만든다.
- Root Key를 단독으로 열 수 있던 device·recovery Slot을 폐기하면 사유와 무관하게 새 무작위 Root Key로 `key_epoch`를 시작하고, 활성 수단의 Slot을 모두 새 Root Key로 다시 만들며 현재 항목을 새 Item DEK로 재암호화한다. 폐기 기기나 복구 수단이 이전 Root Key나 Item DEK를 알고 있어도 새 epoch 이후 상태를 읽지 못해야 한다.
- 분실 기기가 과거에 이미 본 평문은 원격으로 회수할 수 없다. 앱은 연결 지도에서 실제 외부 비밀번호와 API 키 회전 목록을 만든다.

마지막 선택 수단이라도 도난 상황에서는 즉시 폐기를 허용한다. 이후 계정은 `보호 설정 필요` 상태가 된다. 사용자는 기존 항목 읽기·내보내기·삭제·자격 증명 회전을 계속할 수 있지만, 대체 수단을 등록하고 복구 연습을 마칠 때까지 새 Secret 추가는 중단한다.

복구나 key epoch 교체는 준비, 검증, 전환의 단계형 트랜잭션으로 처리한다. 새 checkpoint와 필요한 Slot이 모두 검증되기 전에 이전 세대를 폐기하지 않는다. 네트워크 중단이나 중복 요청은 이전 안전 상태를 유지하고 같은 작업 ID로 재시도할 수 있어야 한다.

마스터 비밀번호와 모든 복구 경로를 잃으면 기존 금고는 복구할 수 없다. 본인 계정 확인 후 새 빈 금고 생성만 제공하며, 운영자 복구처럼 보이는 우회 기능은 만들지 않는다. 새 빈 금고 생성은 기존 ciphertext를 자동 덮어쓰거나 삭제하지 않고 별도 vault ID를 사용한다. 전 계정 채널 통지와 취소 대기시간 뒤에만 새 기본 금고로 전환하며, 기존 암호문 보존·삭제는 공개된 계정 삭제 정책을 따른다.

Google/OIDC 계정을 잃었지만 로컬 ciphertext와 금고 복구 수단이 남아 있으면 로컬 복호화·암호화 export는 가능하다. 그러나 금고 수단만으로 서버 계정 소유권을 자동 이전하지 않는다. 사용자는 미리 등록한 passkey나 다른 계정 인증 수단으로 재결합하거나, 새 서비스 계정을 만든 뒤 로컬 export를 명시적으로 가져와야 한다.

## 8. 롤백과 서버 위협

복구 사건이나 Root Key를 단독으로 열 수 있던 device·recovery Slot 폐기로 `key_epoch`가 바뀔 때마다 단조 증가한 epoch와 암호화·서명 checkpoint를 만든다. 새 Slot 추가와 침해 징후 없는 정상 마스터 비밀번호 교체는 현재 `key_epoch`를 유지하고 새 roster·Slot commitment를 담은 다음 checkpoint만 만든다. `security epoch`라는 별도 이름은 사용하지 않는다. 각 기기는 비반출 wrapping key와 별도의 Ed25519 device signing key를 가지며, revision과 checkpoint의 canonical bytes를 서명한다. checkpoint는 직전 checkpoint hash, 현재 epoch, device roster, 현재 item heads와 tombstone commitment를 포함한다.

정상 변경은 최신 checkpoint hash에 대한 compare-and-swap으로 한 번만 확정한다. 동시 복구 두 건 중 하나만 다음 epoch를 얻고 다른 요청은 취소·재시도 상태가 된다. 서버 인증 계층은 vault `key_epoch`와 별개인 단조 증가 `account_recovery_generation`을 유지한다. 복구 완료 CAS가 두 값을 함께 증가시키고 transition manifest에 결합한다. 세션과 roster는 발급 당시 generation을 가지며 서버는 이전 generation의 새 쓰기를 거부한다. 기존 신뢰 기기는 마지막 checkpoint hash를 보존하고, 서버가 과거 roster나 폐기 전 Slot을 되살리거나 서로 다른 fork를 제시하면 자동 병합하지 않고 동기화를 중단한다. fork의 정본 선택은 사용자가 각 기기의 checkpoint hash를 비교하거나 독립 witness 증거를 검증한 뒤 수행한다.

모든 기기를 잃은 완전 신규 복구 클라이언트는 외부에 기억된 최신 상태가 없으면 악성 서버가 제시한 과거의 정상 서명 checkpoint를 혼자 판별할 수 없다. 강한 targeted rollback 방지는 독립 transparency witness가 있을 때만 보장한다고 표현한다.

서버가 보는 것과 보지 못해야 하는 것은 다음과 같다.

| 서버가 관찰할 수 있음 | 암호문 안에 있어야 함 |
| --- | --- |
| 계정 ID와 로그인 제공자 | 마스터 비밀번호와 복구 키 원문 |
| IP, User-Agent, 요청·복구 시각 | Vault Root Key, Item DEK와 보호자 키 조각 |
| opaque device ID·public key, 수단 종류·상태·개수 | 사용자가 붙인 기기 이름과 금고 항목 내용 |
| 보호자 계정·전달 주소와 요청 상태 | 사이트명, Console URL, 계정·프로젝트·연결 관계 |
| 레코드·revision 수, ciphertext byte, 접근·변경 패턴 | Secret, 메모, 태그와 로컬 검색어 |

암호문 크기, 항목 수와 변경 패턴으로 내용의 일부 특성을 추정할 가능성은 남는다. `제로지식` 약속은 서버가 정상 클라이언트가 만든 암호문에서 위 오른쪽 열의 평문을 직접 복호화할 수 없다는 범위로 표현한다.

## 9. 검증 기준

합성 데이터로 다음을 자동 검증한다.

- 보호 수단 3개·4개·5개 구성의 등록·잠금 해제·복구
- 잘못된 비밀번호, 복구 키와 변조된 Slot 거부
- 잠긴 기기와 잠금 해제된 기기의 분실 시나리오
- 복구 키·기기·물리키·보호자의 폐기와 재등록
- 정상 device·recovery Slot 폐기도 key epoch 회전을 요구하고, 새 Slot 추가와 침해 없는 마스터 비밀번호 교체만 같은 epoch를 유지
- 보호자 한 명 탈취, 두 명 공모와 대기 중 취소
- Android 앱 재설치, Keystore 무효화, OS 백업 복원, 생체정보·화면 잠금 변경과 software-backed 장치
- 복구 중 네트워크 중단, 중복·동시 요청과 원자적 재시도
- 부분 캐시·서버 ciphertext 누락에서 snapshot barrier가 구 epoch 폐기를 차단
- 이전 epoch 소유 증명 없는 새 기기·서버 세션의 transition 거부
- 격리 복구본이 온라인 전역 복구 전에는 원래 vault의 epoch·roster·Slot을 바꾸거나 동기화 쓰기를 만들지 못함
- OIDC 계정 분실·탈취, 로컬 export 재결합과 새 빈 금고 생성 취소
- 과거 DB·앱 상태를 복원해도 폐기 수단이 최신 epoch에서 살아나지 않음
- 복구 완료 뒤 이전 세션·Slot·기기 권한 무효화
- 서버 DB·백업·로그만으로 Root Key와 평문을 복구할 수 없음
- 알림·오류·감사 기록에 Secret과 의미 메타데이터가 없음

실제 Secret 공개 베타는 독립 암호 설계·구현 검토, 침투 테스트, 복구 훈련, 클라이언트 공급망 검토에서 고위험 미해결 항목이 없을 때만 허용한다.
