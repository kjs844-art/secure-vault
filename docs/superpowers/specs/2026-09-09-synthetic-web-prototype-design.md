# Secure Vault 합성 Web Prototype 설계

- 작성일: 2026-09-09
- 기준 커밋: `f85e547b270b3400c924ea8afe9e1f36d846b661`
- 작업 브랜치: `hermes/synthetic-web-prototype`
- 상태: 사용자 승인된 구현 전 설계

## 1. 목적

현재 Rust 암호화·자격 증명 모델·암호문 SQLite 코어는 합성 데이터로 검증됐지만, 사용자가 볼 수 있는 화면은 없다. 이번 단계는 제품 가치를 빠르게 확인할 수 있도록 **React + TypeScript 기반 합성 데이터 전용 Web UI prototype**을 만든다.

사용자가 브라우저에서 다음 흐름을 직접 실행할 수 있어야 한다.

1. 합성 데모 금고임을 확인하고 잠금을 해제한다.
2. 합성 자격 증명 3개를 카드 또는 목록으로 본다.
3. 서비스·계정·프로젝트·환경·태그를 실시간 검색하고 필터링한다.
4. 한 항목의 상세 패널을 열어 연결된 앱/MCP/배포 환경을 본다.
5. `DEMO_VALUE_ONLY_` 접두사가 있는 합성값만 복사한다.
6. 수동으로 다시 잠근다.

## 2. 이번 범위

### 포함

- `apps/web/` 안의 독립 실행 가능한 React + TypeScript 앱
- 단일 페이지의 잠금 화면과 금고 화면
- 타입이 고정된 합성 fixture 3개
- 클라이언트 메모리 내 검색·필터
- 목록/카드와 상세 패널
- Clipboard API를 이용한 합성값 복사 및 짧은 성공/실패 피드백
- 수동 재잠금 시 화면 상태와 검색어 초기화
- 실제 Secret 금지 경고와 합성 모드 표시
- 반응형 레이아웃, 키보드 탐색, 포커스 표시, 기본 스크린리더 이름
- 단위/컴포넌트 테스트와 브라우저 smoke test
- 정적 배포에 필요한 보안 헤더/CSP 예시와 빌드 문서
- 구현 의도, 실제 완료 항목, 검증 증거, 후속 권장사항을 담는 검증 기록

### 제외

- Rust/WASM 연결
- IndexedDB 및 SQLite 연결
- 서버 API, 로그인, 동기화
- 실제 비밀번호·API 키·복구 키 입력 또는 가져오기
- 사용자가 새 Secret을 생성·편집하는 기능
- 실제 백업·복구
- 분석 SDK, 광고, 채팅 위젯, 원격 폰트와 임의의 제3자 JavaScript
- 공개 배포와 `main` 병합

이 prototype은 사용할 수 있는 비밀번호 관리자가 아니며, 실제 자격 증명을 다루는 것처럼 표현하지 않는다.

## 3. UX 구조

### 잠금 화면

- 제품 작업명과 `SYNTHETIC DEMO` 배지
- 실제 자격 증명을 입력하지 말라는 눈에 띄는 경고
- 자유 입력 비밀번호 필드는 두지 않는다.
- `합성 데모 금고 열기` 버튼으로만 진입한다.

### 금고 화면

- 상단: 제품명, 합성 모드 배지, 현재 항목 수, `다시 잠그기`
- 왼쪽/상단 검색 영역: 전체 검색과 종류·환경 필터
- 본문: 자격 증명 카드 목록
- 오른쪽 또는 모바일 하단: 선택 항목 상세 패널
- 빈 검색 결과와 복사 실패를 별도 상태로 표시

### 합성 항목

정확히 세 가지 관계 형태를 보여 준다.

1. 연결되지 않은 API 키
2. 하나의 MCP 연결에 연결된 자격 증명
3. 여러 앱·MCP·배포 환경이 사용하는 자격 증명

모든 민감값 모양의 데이터는 `DEMO_VALUE_ONLY_` 접두사를 사용한다. 실제 서비스 토큰 형식과 혼동될 수 있는 접두사·길이 패턴은 사용하지 않는다.

## 4. 컴포넌트와 경계

- `App`: locked/unlocked 상태와 전체 화면 조합
- `UnlockScreen`: 합성 전용 진입 경고와 버튼
- `VaultHeader`: 상태·항목 수·재잠금
- `SearchToolbar`: 검색어와 필터 제어
- `CredentialList` / `CredentialCard`: 검색 결과 표시와 선택
- `CredentialDetails`: 관계 정보와 합성값 복사
- `CopyButton`: Clipboard API 성공·실패 피드백
- `fixtures`: 읽기 전용 합성 데이터
- `search`: 정규화된 순수 검색 함수

UI, 검색 로직, fixture, 브라우저 API 경계를 분리해 후속 Rust/WASM adapter가 들어올 때 화면을 다시 작성하지 않도록 한다. 이번 단계에서는 별도 네트워크 adapter나 persistence adapter를 만들지 않는다.

## 5. 상태 및 데이터 흐름

```text
잠금 상태
  └─ 합성 데모 열기
       └─ 메모리의 읽기 전용 fixture 로드
            ├─ 검색/필터 → 파생된 결과 목록
            ├─ 항목 선택 → 상세 패널
            ├─ 합성값 복사 → 일시적 상태 메시지
            └─ 다시 잠그기 → 선택/검색/필터/메시지 초기화
```

페이지 새로고침 시 다시 잠금 상태로 시작한다. URL, localStorage, sessionStorage, IndexedDB, 쿠키에는 항목 또는 검색어를 기록하지 않는다.

## 6. 보안 및 실패 처리

- 자유 형식 Secret 입력 UI를 만들지 않는다.
- fixture 외부에서 데이터를 읽는 코드 경로를 만들지 않는다.
- 네트워크 요청을 하지 않는다.
- HTML 문자열 주입 API를 사용하지 않는다.
- Clipboard API 거부/미지원 시 값 노출 범위를 늘리지 않고 실패 메시지만 표시한다.
- 복사 성공 메시지는 합성값 자체를 반복 표시하지 않는다.
- 정적 호스팅 CSP는 기본 `default-src 'self'` 정책을 기준으로 문서화한다.
- 테스트·스크린샷·로그에도 실제 자격 증명을 사용하지 않는다.

## 7. 테스트 및 완료 기준

다음이 모두 통과해야 완료로 판정한다.

- 잠금 상태에서 금고 내용이 렌더링되지 않는다.
- 데모 진입 후 정확히 3개 항목이 보인다.
- 대소문자와 앞뒤 공백을 무시한 검색이 서비스·계정·프로젝트·환경·태그·연결처에서 동작한다.
- 필터와 검색을 함께 적용할 수 있다.
- 항목을 선택하면 관계 정보가 상세 패널에 나타난다.
- 복사 성공과 거부 경로를 모두 테스트한다.
- 다시 잠그면 선택·검색·필터·복사 상태가 초기화된다.
- 키보드로 주요 동작에 접근할 수 있고 자동 접근성 검사에 중대 오류가 없다.
- lint, typecheck, unit/component tests, production build, browser smoke test가 exit 0이다.
- 정적 번들에서 실제 토큰 패턴과 금지된 외부 네트워크 URL을 검사한다.
- 실행 중인 화면을 메인 PC 브라우저에서 확인한다.

## 8. 5대 병렬 작업 분할

각 작업은 새 터미널, 독립 clone/worktree, 독립 브랜치를 사용한다. 기존 OpenClaw 터미널·폴더·프로세스·포트를 건드리지 않는다.

1. **Worker UI Shell**: 앱 scaffold, 잠금/금고 레이아웃, 반응형 스타일
2. **Worker Domain/Search**: fixture 타입, 합성 데이터, 검색·필터 순수 함수와 테스트
3. **Worker Interaction**: 상세 패널, 복사 상태, 재잠금 상태와 컴포넌트 테스트
4. **Worker QA/A11y**: 브라우저 smoke, 키보드·접근성, 빈 결과·오류 시나리오
5. **Worker Security/Docs**: CSP·외부 요청 금지·secret pattern 검사, README와 최종 검증 기록

공유 계약은 통합자가 먼저 고정한다. 같은 파일을 여러 worker가 동시에 수정하지 않는다. 병합 순서는 Domain/Search → UI Shell → Interaction → QA/A11y → Security/Docs로 하며, 각 병합 뒤 빠른 검증을 실행한다.

## 9. 충돌 방지 및 중단 조건

- OpenClaw Gateway는 명령 전달 통로로만 공유하고 기존 OpenClaw 세션에는 메시지를 보내지 않는다.
- 기존 dirty worktree `secure-vault-sqlite-store-design`은 읽거나 수정하지 않는다.
- 기준은 clean commit `f85e547`로 고정한다.
- 각 PC에서 저장소·브랜치·터미널 제목·개발 서버 포트를 분리한다.
- 동일 브랜치 push, force-push, Gateway 재시작, 노드 설정 변경은 하지 않는다.
- 기기에서 필수 Git/Node 도구가 없거나 clone/auth가 실패하면 해당 worker는 코드 변경 없이 preflight 증거만 남기고 중앙 worker로 재배치한다.
- 실제 자격 증명처럼 보이는 데이터가 발견되면 작업을 즉시 중단하고 값은 출력하지 않는다.

## 10. 원격 기기 작업 수명과 정리

- 작업 시작 전에 PC별 전용 루트와 생성 파일 목록을 기록해 정리 allowlist로 사용한다.
- 작업 중에는 clone/worktree, worker 브랜치, 임시 실행 스크립트, 빌드 산출물과 로그를 해당 전용 루트 안에만 만든다.
- 이번 작업이 구현·통합·GitHub push·최종 검증까지 끝나기 전에는 원격 기기 작업물을 삭제하지 않는다.
- 작업 완료 확인 뒤 각 원격 PC에서 이번 작업이 만든 정확한 경로, 임시 브랜치, 터미널·개발 서버 프로세스와 임시 설정만 삭제한다.
- 기존 저장소, 사용자가 만든 파일, 전역 Git/Node 설정, 인증 정보, OpenClaw, Tailscale, SSH, 다른 프로젝트와 다른 에이전트 작업물은 정리 대상에서 제외한다.
- wildcard 또는 광범위 재귀 삭제 대신 시작 시 기록한 exact-path allowlist를 사용한다.
- 정리 뒤 대상 경로 부재, 관련 프로세스·포트 종료와 중앙 GitHub 브랜치 보존을 다시 확인한다.

## 11. GitHub 기록

구현 브랜치에는 다음을 함께 포함한다.

- 이 설계: 무엇을 하려 했는지와 선택 이유
- 구현 계획: worker별 파일 소유권과 검증 명령
- 최종 검증 기록: 실제로 한 일, 하지 못한 일, 명령별 결과
- 후속 권장사항: Rust/WASM·IndexedDB 암호문 adapter, recovery, backup/restore, 보안 게이트 순서
- 실제 Secret 금지와 `main` 병합 차단 상태

push 또는 PR을 만들 때도 기존 Draft PR의 보안 판정을 덮어쓰지 않고 별도 prototype 브랜치로 유지한다.
