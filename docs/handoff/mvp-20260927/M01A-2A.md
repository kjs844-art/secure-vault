## 목표와 허용 경로

기존 HTTP 테스트는 Fetch 객체를 직접 전달한다. 이번에는 테스트가 소유한
127.0.0.1 임시 서버에서 실제 HTTP 요청을 보내 경계와 cleanup을 검증한다.
**공개 서비스 대상 검사나 실제 인증/DB 검사가 아니다.**

- 새 `apps/benefits-web/tests/catalog-http-loopback.test.ts`
- 새 `apps/benefits-web/tests/support/catalog-http-loopback.ts`
- 새 `docs/verification/mvp-integration/catalog-http-loopback/**`
- 이 M01A-2A.md의 상태/검사 기록만 갱신

운영 source/routes/server, 기존 test/helper, manifest/lock, CI, smoke-server,
경계 검사와 다른 배정 문서는 수정하지 않는다. 발견한 production 결함은 주 담당에게 보고한다.
M05A의 vault 브라우저 QA와 별개이며, M01A-1A를 기다리거나 가져올 필요가 없다.

## 구현 기준

먼저 [HTTP 계약](../../../apps/benefits-web/HTTP_CONTRACT.md), 기존 HTTP tests,
`tests/support/review-memory-store.ts`를 읽는다.

- 기존 Node 내장 HTTP만 사용, 127.0.0.1의 OS 선택 port(0), 합성 세션/입장/메모리 store.
  서버와 요청은 테스트가 직접 만들고 finally에서 해당 socket/server만 정리한다.
- 실제 catalog handler를 호출하되 fixture를 운영 route에 mount하지 않는다.
  요청 변환은 streaming/AbortSignal을 보존하고 Request 생성 전에 무제한 buffering하지 않는다.
- 정상 CRUD와 same-operation retry, origin/custom-header/media/body 제한 및
  고정 오류/no-store/no-CORS를 실제 요청·응답으로 확인한다.
- 세션 전환, 늦은 응답, 요청 중단·기한 후 다른 요청 정상 처리, 자원 정리를 검증한다.
  연결 중단 뒤 write가 없었다고 추측하지 말고 fixture commit 상태를 별도 확인한다.
- 전체 앱 suite에서 안정적인 timeout 여유와 이벤트 기반 동기화를 사용한다.
  반복 부하/공개 target probing/포트 스캔/외부 DNS/메일/API/실제 인증은 하지 않는다.
- 실제 Node HTTP framing에서 거절된 요청과 handler가 거절한 요청을 구분한다.
  proxy/TLS/브라우저 cookie/CORS 정책/운영 DB까지 검증했다고 주장하지 않는다.
