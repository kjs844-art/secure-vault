# KeyAtlas — 작게 먼저 배포하기 / 작업 시작점

2026-09-27 KST. 사용자 결정: 기능을 줄여 먼저 배포하고 점진적으로 발전시킨다.
이 문서는 그 결정의 실행 계획이며, 배포 완료나 실제 Secret 허용 증거가 아니다.

## 현재 가장 중요한 결정

- 첫 웹의 출발점은 **benefit-validator**다. 이미 KeyAtlas 이름의 /demo, 계정,
  Gmail 분석, 서비스/혜택 화면, 내보내기 코드가 존재한다. 이번에는 운영 E2E를 실행하지 않았다.
- **secure-vault**는 암호화 금고/Worker/WASM/로컬 저장 경계를 맡는다.
  실제 Secret 허용은 CLOSED다. 금고 기능 때문에 모든 공개 화면의 배포를 기다리지 않는다.
- 지금은 제품 메뉴와 연결 계약을 통합한다. Git 이력, DB, 세션, 복호화 키를 물리적으로
  합치는 작업은 하지 않는다. 두 repo/별도 origin으로 시작하면 보안 경계와 Lovable 이력을 보존할 수 있다.
- 기존 100개 브랜치는 장기 backlog다. 첫 배포를 위해 전부 완료할 필요는 없다.
  이번 **M01A~M06의 6개 우선 작업**만 활성 배정 대상으로 삼는다.
- 신규 브랜치는 작업 메모가 들어간 작업 장소다. 브랜치 생성은 해당 기능 구현을 뜻하지 않는다.

## 먼저 배포할 것과 다음 단계

| 단계 | 사용자가 얻는 것 | 완료 기준 | 예상 작업량 |
|---|---|---|---|
| P0 공개 체험판 | /demo에서 서비스·혜택·만료·확인 필요를 탐색 | 합성 데이터, 모바일/키보드 동작, 실제 공개 HTTPS 주소에서 검증, 서버/API 경계 확인·롤백 가능 | 집중 작업 1~3일, 환경 준비 포함 대략 2~5일 목표 |
| P1 제한 Gmail 파일럿 | 본인 승인 메일에서 가입·혜택 후보 찾기→확인/수정→저장→삭제 | 사용자별 권한/RLS 적용, 최소권한 OAuth, AI 전송 동의, 토큰·로그 보호, 제한 비용/레이트, 운영 E2E | 현재 코드 기반 집중 작업 약 1~3주 + 외부 심사·계정 준비 대기 |
| P2 통합 계정 지도 | 서비스와 API 사용처/MCP 관계를 비밀 원문 없이 정리 | M03 계약+사용자 확인+연결 끊기, 개인정보 최소화, 기능별 데이터 경계 검증 | 파일럿 이후 1~2주 규모로 재산정 |
| P3 실제 Secret 금고 | 비밀번호/API key 원문 저장·재인증·보기·복사 | 복구·기기 분실·수명주기·데이터 보존·독립 보안 리뷰·운영 대응까지 통과 | 미해결 보안 검증 후 재산정; 이번에 날짜 확약 안 함 |

예상치는 전담 작업·신규 대규모 재설계 없음·검토 가능을 전제로 한 계획 범위다.
여러 AI 수로 작업기간을 나누지 않는다. 공급자 승인·보안 심사·DNS·사용자 결정은
병렬 코딩으로 없애지 못한다. 이전 5~6개월은 전체 제품에 대한 거친 추정이며,
앞으로 6개월을 더 기다려야 한다는 측정값이 아니다.
**P0는 체험판 출시이고 Gmail 서비스나 실제 비밀번호 금고 완성이 아니다.**
Gmail은 핵심 수집 기능으로 P1에서 바로 이어가며 수동 메모 앱으로 대체하지 않는다.

P0 공개 때 실제 로그인·메일·AI·MCP가 같은 배포에 존재한다면 메뉴만 감추는 것으로
닫혔다고 보지 않는다. 서버에서도 실제 처리 경로가 차단/격리되어야 한다.
현재 그런 차단이 구현됐는지는 M04A/M06에서 확인한다. 미확인 상태는 공개 준비 미완료다.

P0에 없는 것: 실제 비밀번호/API key 보관, 클라우드 금고 동기화, 결제, Android/iOS,
생체인증·분실 복구, 자동 탈퇴/삭제, 자동 키 회전, Ethereum/블록체인.
기존 전체 설계를 폐기하는 것이 아니라 해당 기능을 후속 단계로 옮긴다.

A: 보안·통합·검증 판단이 필요한 작업. 특정 모델을 지정하지 않는다.
M02/M06은 상대적으로 가벼운 AI에, M03은 테스트 가능한 코딩 AI에,
M04A/M05A는 검토·실제 브라우저 검증 가능한 AI에 맡기기 적합하다.
무료 채팅 사용 가능 여부와 API 요금은 별개이며 특정 도구 구매를 요구하지 않는다.

각 링크는 **그 작업 브랜치에 있는 MD**다. 한 번에 한 AI만 배정한다.
사용자가 고른 AI는 해당 MD 마지막 프롬프트를 받고, 원격 tip과 로컬 상태를 확인한 뒤
자기 작업 폴더에만 수정한다. 공유 App/Shell·암호 코어·인증·DB는 주 담당과 소유권을 맞춘다.

## 진행 순서

1. M02/M04A/M06 병렬: 기존 demo 정리, 메일/서버 경계 검토, 실제 호스팅 절차 확인.
2. M01A: 그 결과에서 P0 필수 차단만 해결하고 배포 후보를 선정한다.
3. 사용자: 실제 배포 계정/대상 URL과 비용 상한을 지정한다. 제공자 기본 HTTPS 주소로
   먼저 시작할 수 있는지 확인한 뒤, 사용자 소유 도메인은 나중에 연결해도 된다.
4. 후보 SHA의 build/필수 테스트/실제 브라우저와 공개된 URL의 스모크 검증을 구분한다.
5. P0를 게시하고 5분 체험 피드백을 수집한다. 이 문서 작성은 게시 수행이 아니다.
6. P1의 별도 Gmail 동의·데이터 처리/삭제·비용 검증을 끝내 제한 사용자 파일럿을 진행한다.
7. M03/P2와 실제 Secret 금고 P3를 단계적으로 통합한다.

## 사용자가 준비할 것

- 당장: 먼저 맡길 AI와 작업 번호 선택, 현재 benefit/Lovable 배포 계정·주소 확인,
  최초 테스트할 사람/기능 범위 선택, 월 비용 상한 결정.
- 실제 메일 파일럿 전: OAuth 앱/검증 책임 계정, 개인정보 처리·외부 AI 전송 동의,
  운영자 연락처, 로그 보관/삭제 및 테스트 동의.
- 뒤로 미뤄도 됨: 유료 도메인 구매, 결제 플랜, 앱스토어 계정, 블록체인.
- 키/비밀번호/메일 원문은 채팅이나 Git에 넣지 않는다. 설정이 필요한 시점에
  제공자 콘솔의 비밀 관리 기능에서 사용자가 입력한다.
