# benefit-validator + secure-vault 연결 경계

상태: PROPOSED / 합성 데이터 계약부터. 2026-09-27.
기준: benefit 954da8da0b12d55a342d187fab17abe57b93fbb0; vault 34b43e1a5d2f1d81eb2f6456d657fd04ca57332f.

## 같은 제품, 다른 데이터 경계

~~~text
KeyAtlas 웹·계정·혜택 (benefit-validator)
  ├─ /demo: 합성 체험 → 첫 배포 후보
  ├─ 로그인·Gmail 별도 동의 → 메일 근거 후보 → 사용자 확인
  └─ 서비스 참조/확인 상태 ── 사용자 명시적 선택 ── 연결 계약
                                                     │
별도 vault origin (secure-vault)                      │
  └─ 클라이언트 잠금 해제 → 암호화 금고 → 키 참조/사용처
     실제 비밀번호/API key는 별도 게이트 통과 전 비활성
~~~

공유 로그인 자체가 금고 복호화 권한은 아니다. 서로 다른 origin의 쿠키, localStorage,
OAuth 토큰, 금고 Root Key, IndexedDB를 자동 공유하지 않는다.
첫 연결은 메뉴/출처 안내와 합성 참조 계약이다. 실제 cross-origin API/postMessage 구현은
origin allowlist·사용자/세션 결속·재인증·회수·재전송 방지 검토 이후에만 한다.
광고/분석/외부 스크립트가 있는 웹 셸에 잠금 해제된 금고를 삽입하지 않는다.

## 최소 교환 정보

- 공개 서비스 식별자, 사용자에게만 의미 있는 불투명 참조 ID
- 확인됨/후보/확인 필요 구분, 근거 종류, 관찰 시각
- 선택적으로 공개 도움말 주소 (query/토큰/개인 URL 제외)
- 각 필드도 연관되면 개인정보가 될 수 있다. 사용자 권한 확인/삭제/최소화가 필요하다.

금지: 비밀번호·API key 원문·메일 원문·제목·세션/OAuth 토큰·복구 키·결제정보.
참조 ID를 권한 증명으로 사용하지 않는다. 임의 URL을 서버가 가져오는 기능은 포함하지 않는다.
코드 구현 전 입력 상한·타입·버전·중복·freshness·거부 규칙을 M03에서 정한다.

## 메일과 금고의 보장 차이

benefit 서버의 연결키 암호화는 서버가 복호화해 API에 접근하는 형태다.
secure-vault의 운영자 접근 불가 목표와는 다르다.
메일 원문 전체를 DB에 저장하지 않는다는 설명으로 외부 AI 전송이 없다고 주장하지 않는다.
메일 분석 전 외부 처리 경로와 범위·수집/보관/삭제를 사용자에게 설명하고 동의를 받는다.
실제 메일·토큰·운영 DB는 이번 설계 검토에 사용하지 않는다.
