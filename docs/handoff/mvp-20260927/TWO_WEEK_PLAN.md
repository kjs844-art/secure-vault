Gmail은 핵심 수집 경로다. 외부 OAuth 승인·운영 검증이 남으면 그것을 별도 미완료로 기록하고
공개 가능한 subset만 표시한다. 실제 비밀번호/API key 금고의 복구·분실·독립 감사는 별도 단계다.
날짜를 맞추려고 검증 안 된 경로를 활성화하지 않는다.

## DB·서버·도메인: 새로 필요한가?

| 항목 | 현재 사실 | 이번 방향 |
|---|---|---|
| DB 코드 | 참고 repo에 Supabase 클라이언트·Drizzle migration·RLS 코드 있음 | 코드만 이식. 운영 DB가 따라오는 것은 아님 |
| 원본 DB | Lovable 프로젝트는 사용자가 지금도 열 수 있다고 확인. 실제 DB 소유/권한/상태는 미검증 | 당분간 원본 영향 없이 별도 개발·배포 환경을 기본 후보로 계획 |
| 새 DB 계정 | 아직 결정 안 함 | 기존 본인 Supabase 계정이 있다면 그 계정 내 새 프로젝트를 후보로 검토. 새 회사/이메일 계정부터 만들 필요는 없음 |
| 서버 | TanStack SSR·서버 함수가 필요 | 정적 파일 호스팅만으로 전체 기능 운영 불가. 선택할 플랫폼의 호환 런타임 확인 |
| 도메인 | KeyAtlas용 확정 이름·소유권 미확인 | 플랫폼 기본 HTTPS 주소로 먼저 테스트. 정식 이름은 2주차 연결 가능 |
| 비용 | 현재 계정 플랜·잔여 무료 용량·월 한도 미확인 | 생성/과금 전에 사용자 예산을 정하고 실제 한도를 확인 |

원본 보존 요청이 있으므로 **원본 DB 공유를 자동 선택하지 않는다**.
새 테스트 프로젝트를 준비하면 사용자의 Lovable 앱과 데이터를 건드리지 않고 migration/RLS를 검증할 수 있다.
추후 원본 DB 연결을 재사용하려면 사용자 결정과 영향 검토가 별도로 필요하다.
원본 DB 삭제·초기화·데이터 이전·키 회전은 이번 계획에 포함되지 않는다.

Lovable 내장 Cloud는 Supabase 기반 DB/인증/서버 기능을 포함하지만, 코드만 다른 repo로
옮겼다고 서비스 접근권한/사용자/비밀 설정이 함께 이전되는 것은 아니다.
별도 Supabase 프로젝트를 선택해도 auth/owner RLS/함수/환경 분리는 검증해야 한다.
새로운 DB가 무조건 무료이거나 원본과 자동 분리된다고 주장하지 않는다.

공식 참고(2026-09-27 확인):
- [Lovable Cloud 구조](https://docs.lovable.dev/features/cloud)
- [Supabase 개발·운영 환경 관리](https://supabase.com/docs/guides/deployment/managing-environments)
- [Lovable 기본 주소와 사용자 도메인](https://docs.lovable.dev/features/custom-domain)

참고로 Lovable의 새 custom domain 연결은 현재 유료 플랜 대상이다.
원본 Lovable 도메인을 지금 바꾸지 않는다. 새 KeyAtlas 호스팅을 선택하면 그 플랫폼의
기본 주소/도메인/SSR 지원/가격을 다시 확인한다. 이번에 도메인을 구매하거나 서버를 만들지 않았다.

## 사용자 개입

- 지금 확인된 것: 원본 Lovable 프로젝트는 열리며 당분간 그대로 보존한다.
- 1~2일: KeyAtlas 배포를 위한 본인 클라우드/DB 계정과 월 비용 상한 선택.
- 실제 Gmail 파일럿 전: OAuth/메일 읽기 동의·테스트 계정·외부 AI 처리 범위·비밀 설정.
- 도메인 연결 전: 원하는 이름·등록 소유자·구매 여부.
- 실제 공개 전: 공개/초대 범위와 운영 연락처·배포 후보 확인.

AI가 먼저 할 수 있는 일은 코드 이식 분석, 합성 화면/테스트, 보안·권한 검토, migration와
운영 문서 준비다. 비밀값은 채팅/Git가 아니라 선택한 제공자의 비밀관리 화면에서 입력한다.
