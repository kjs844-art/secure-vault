## 6. 외부 AI에 절대로 보내면 안 되는 데이터

- 실제 비밀번호·API 키·Secret·복구 키·session cookie
- 키의 일부와 email이 함께 보이는 console screenshot
- 실제 이름·email·account ID가 보이는 화면
- `.env`, DB/WAL, IndexedDB export
- 개인 vault의 암호화 backup
- production log, HAR, crash dump
- SSH private key, Android signing key, OAuth client secret
- GitHub Actions Secret, Cloud IAM 정보
- 수정 전에 공개되면 위험한 취약점 보고서

무료 plan이라고 해서 입력 데이터가 자동으로 비공개이거나 학습에서 제외된다고 가정하지 않는다. 각 서비스의 보관·학습·공개 preview 설정을 먼저 확인한다.

## 7. GitHub 연결 권한

가장 안전한 순서:

1. 필요한 파일만 복사한 합성 작업 묶음을 제공한다.
2. 가능하면 별도 fork 또는 작업 전용 복사본을 사용한다.
3. GitHub App을 연결한다면 저장소 Contents의 필요한 권한만 허용한다.
4. Settings, Actions Secrets, Webhooks, Environments, Administration 권한은 주지 않는다.
5. 개인 PAT·SSH private key를 prompt에 붙여 넣지 않는다.
6. 작업 후 연결 권한과 token을 철회한다.
7. 결과는 해당 branch에만 push하고 Draft PR로 검토한다.

GitHub App 권한이 실제로 특정 branch만 제한하지 못할 수 있다. 따라서 “이 branch만 수정”은 기술적 강제라기보다 작업 규칙일 수 있으며, 민감 저장소 전체 접근이 불편하면 필요한 파일만 제공하는 별도 fork가 더 안전하다.

## 9. 병합 전 신뢰 리뷰 체크리스트

- [ ] 지정된 허용 파일만 변경했는가
- [ ] 보안 핵심·금지 파일 변경이 0개인가
- [ ] 새 dependency·install script가 0개인가
- [ ] 외부 analytics·telemetry·font·network call이 0개인가
- [ ] 실제 개인정보·Secret·부분 key가 0개인가
- [ ] 합성 fixture가 실제 key처럼 오인되지 않는가
- [ ] 관련 test·typecheck·build가 통과했는가
- [ ] Secret scan과 `git diff --check`가 통과했는가
- [ ] AI가 실행하지 못한 검사를 숨기지 않았는가
- [ ] 라이선스·이미지 출처가 명확한가
- [ ] 현재 CI 기준점에 안전하게 재적용됐는가
