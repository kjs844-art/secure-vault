## 사용자 흐름과 코드 위치

```text
합성 금고 목록/검색 → 별도 백업 화면 (목록 세션은 잠김)
  ├─ 사용 확인 → 저장된 암호문 검증 → Blob 다운로드 링크
  │                                      └─ 브라우저의 실제 파일 저장은 별도 결과
  └─ 사용 확인 → File 선택(크기만) → 복원 버튼 → 파일 읽기
                         → Worker/WASM 인증 → 빈 IndexedDB에만 생성
                         → 동일 바이트 readback → 명시적 다시 열기

숨김/이탈/5분 유휴/취소 → 사용 확인·File 참조·URL 해제 → 이전 비동기 결과 무시
```

## 실제 브라우저 증거

`agent-browser` 스킬을 사용해 별도 headless Chrome 세션과 `127.0.0.1:4187`의 로컬 production preview를 사용했다.
일상적으로 사용하는 Chrome 프로필/로그인에는 연결하지 않았다.

확인:

1. 합성 금고 생성/열기 3개 → `Example CLI` 검색 1개 → 잠금으로 목록/검색 제거 → 다시 열어 빈 검색어/전체 분류/3개 복구.
2. 백업 화면 최초 사용 확인 해제, 파일 선택/백업/복원 비활성. 확인 후 암호문 검증과 Blob 링크 준비.
3. 다른 탭으로 전환 후 돌아오면 사용 확인과 다운로드 링크가 제거됨. 자동으로 다시 열리지 않음.
4. 내보내기가 준비한 3892바이트 합성 암호문을 브라우저 안에서 읽어 별도의 빈 테스트 브라우저에 `File`/`DataTransfer`로 전달. 실제 파일 읽기 API·UI 복원 버튼·Worker/WASM·IndexedDB를 거쳐 복원 완료.
5. 복원 화면에서 링크를 눌러 금고로 돌아오면 잠김. 명시적으로 열어 항목 3개와 MCP/CLI/CI 관계 확인.
6. 복원본을 다시 내보내기 준비해 원본 SHA-256과 일치 확인. 이미 금고가 있는 상태의 재복원은 거부되고, 재검증한 암호문 해시도 동일.

### 미검증: 디스크 다운로드와 네이티브 파일 선택

CLI download 보조 명령과 일반 링크 클릭 모두 테스트 Chrome에서 `Failed - Download error`로
끝났고 실제 파일은 저장되지 않았다. 별도 임시 폴더, 실행 시 `--download-path` 지정에서도 같은
결과였다. 링크는 살아 있고 브라우저 내 Blob 읽기는 정상이며, 앱 상태가 취소된 것으로 확인되지는
않았다. 그러나 이 관찰만으로 브라우저/OS/도구 중 하나를 확정 원인이라고 단정하지 않는다.

위 4–6번은 **디스크 파일을 다운로드·선택한 E2E 성공이 아니다.** 테스트 드라이버가 준비된 합성
암호문을 다른 브라우저의 File API로 전달했다. 네이티브 파일 선택기, 실제 디스크 파일 왕복,
모바일, 실제 5분 대기, OS 절전·기기 분실 복구는 확인하지 않았다. 유휴/절전/취소 순서는 자동
이벤트 대역 검사로만 증명했다. 다운로드 문제 해결에는 별도의 지원 환경 확인이 필요하다.

검사 후 직접 만든 격리 브라우저 3개의 close 성공을 확인하고, 직접 시작한 preview만 정상 중단 요청했다.
사용자 브라우저/IDE/다른 작업을 종료하지 않았다. 합성 암호문/브라우저 프로필/다운로드 시도 산출물은
Git 스테이징 대상에 넣지 않았다. 고신뢰 패턴 검사 0건은 완전한 비밀정보 부재나 보안 감사의 보증이 아니다.
